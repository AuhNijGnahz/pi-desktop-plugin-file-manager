目标场景：file-manager 右键 HTML → 在 pi.browser 视图中打开
file-manager希望「在浏览器插件中打开」
✗

ADR 0262 明确 Rejected for now；HOST_API_ALLOWLIST 无 plugins.*；desktop.control 目录无 open view 操作
提案路径（未落地）openTargets + pi.plugins.open

listOpenTargets → consent → 标准投递 → 目标视图
需 ADR 修订 + 权限矩阵 + 传输兼容（见下方评审要点）

为什么现有 API 到不了目标

ui.openPanel：只打开调用方自己的面板。
pi.plugins.*：不在 allowlist，SDK 未定义。
view:open 通用投递：仅宿主 Renderer/Main 写入；且 pi.browser 特判不走该通道。
fs.openDefault：落到系统浏览器，不是工作面板插件。

8. 多子代理评审摘要（提案 openTargets）

优点（三路一致）

  • 补齐 ADR 0262 点名搁置的真实缺口
  • 未声明 openTargets → fail-closed
  • 复用 piViewOpen / view:open，不另造进程模型
  • 原生同意 + schema 字段展示，禁止调用方自由文案
  • 不切换工作区、不做通用 RPC，边界清晰

缺陷（优先修）

  • HIGH 第三方可向 fm 投递绝对路径 → 事实上的 external fs 特权
  • HIGH Always-allow A→B = 常驻能力，与 ADR 0208 冲突
  • HIGH pi.browser 不走 view:open，通用投递打不开浏览器
  • HIGH schema 不机检则静默空态，生态更差
  • MED viewId 不可省；plugins.list 冗余，应 listOpenTargets
  • MED 信封必须宿主盖章 fromPluginId；查询串保持 path 字符串

三路综合结论

方向正确，不可原样上线（Ship-with-changes）。 落地前必须：ADR 修订；listOpenTargets + 必填 viewId；投递加法式 { path?, open? } 且 query 仍为字符串； 权限 ui.openTargets.read/open 入矩阵与 allowlist；默认「允许一次」；宿主按 fromPluginId 做路径类别过滤（禁 dataDir/scratch 绝对路径进第三方 open）； pi.browser 走 browserHost 特殊适配 而不是通用 view:open。在此之前，优先窄场景：宿主中介的「工作区 HTML → 浏览器视图」。
